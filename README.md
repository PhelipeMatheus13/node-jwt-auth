# JWT Authentication API

A simple and secure authentication API built with Node.js, Express, and PostgreSQL. It implements JWT-based authentication with access and refresh tokens, role-based authorization, input validation, DTOs, and a clean modular architecture. The project includes comprehensive unit and integration tests using ephemeral PostgreSQL containers.

## Features

- User registration with password hashing (bcrypt)
- User login returning access and refresh tokens (JWT)
- Role-based access control (admin / user)
- Admin-only routes (delete any user) and ownership protection
- Refresh token rotation with sliding expiration and atomic database transactions
- JWT ID (JTI) for per-token identification and reuse detection
- Automatic revocation of all user tokens on suspicious reuse
- Logout and global logout (all devices)
- Centralized error handling with custom `AppError` and `asyncHandler` wrapper
- Input validation with express-validator
- DTO layer for consistent input/output formatting and JSDoc type annotations
- Repository pattern for data access
- SQL migrations with Knex.js
- Scheduled job for cleaning expired and revoked tokens (background worker)
- Structured logging with Pino and request context propagation (AsyncLocalStorage)
- Automatic redaction of sensitive data in logs
- OpenAPI/Swagger documentation with interactive UI
- Unit and integration tests with Jest, Supertest, and testcontainers
- Dockerized development environment

## Code Conventions

This was my first indie project built entirely from scratch. At the beginning, the repository didn't have a strict coding philosophy, which naturally led to some syntax variations during early development. To ensure long-term maintainability, professional quality, and a unified structure, a global code style refactoring was applied with the following strict conventions:

- **Arrow Functions**: Adopted as the standard for all internal application logic. Every controller, service, repository, middleware, and utility function is declared as a constant arrow function to ensure consistent scoping and visual harmony.
- **Regular Functions**: The use of regular functions must be justified and documented. Database migrations and seeds utilize this syntax because the Knex.js CLI generates and tracks these infrastructure files natively, ensuring seamless integration with the Knex.js ecosystem.
- **File Naming**: All modules follow the `name.type.js` convention (e.g., `auth.controller.js`, `auth.service.js`, `auth.middleware.js`) to make the purpose of each file immediately clear and to keep the project structure predictable.
- **JSDoc**: Public functions, DTOs, and middlewares are documented with JSDoc annotations to provide inline type hints, clarify contracts, and complement the OpenAPI documentation generated by Swagger.
- **Spacing**: A strict 4-space indentation rule is applied across the entire codebase (including source code, Docker Compose, and OpenAPI documentation) to maximize readability. However, files automatically managed or overwritten by Node.js tools (`package.json` and `package-lock.json`) retain the default 2-space indentation to avoid conflicts with the tools.


## Database Setup (Development)

Start the PostgreSQL container
```bash
docker compose up -d
```
Run migrations 
```bash
npx knex migrate:latest
```
Running the Application
```bash
npm start
```
Stop the database when done
```bash
docker compose down
```

## Notes

> ⚠️ You must have Docker installed and properly configured, and be running in a Linux-based environment (or WSL on Windows) for the project to work correctly.

> Some files are excluded from coverage (`coveragePathIgnorePatterns`) because they are configuration/bootstrap code rather than business logic: `server.js` and `app.js` (application entry points and wiring), `database.js` (Knex connection setup), `logger.js` / `http-logger.middleware.js` (Pino/Pino-HTTP configuration), the Swagger docs setup, and `rate-limiter.middleware.js` (a thin wrapper around `express-rate-limit` configuration). Their behavior is validated manually in development, while any business logic that depends on them is covered by tests in the consuming modules.

> This project uses IP-based rate limiting to mitigate brute-force attacks. Account-based lockout (blocking a specific account after N failed attempts, regardless of source IP) was considered but intentionally not implemented — it would require additional complexity (failed-attempt tracking per user, unlock logic, and countermeasures against third-party lockout abuse) that isn't justified for a project without real users or a genuine attack surface.

> Rate limiting uses the in-memory store (default in `express-rate-limit`), which is sufficient since this project runs as a single process and isn't intended to scale horizontally. A distributed store (e.g. Redis) would be required for a multi-instance deployment; the rate limiter is already structured (`createRateLimiter` factory) so swapping the store later is a config change, not a rewrite.

> Email verification and password reset were intentionally left out of this project. They were considered, but concluded to be more about "product completeness" than additional authentication depth — the core hard problems of this project (token rotation, reuse detection, RBAC) are already solved, and adding email-based flows here would mean new infrastructure (email provider integration, a new table for verification/reset codes, new rate-limited routes, and their own test suite) without new technical learning. 

> `npm audit` reports vulnerabilities exclusively within Jest's internal dependency tree (`@jest/reporters`, `@jest/transform`, `babel-plugin-istanbul`, `test-exclude`, and their transitive `glob`/`minimatch`/`brace-expansion` dependencies). These are devDependencies used only for test coverage instrumentation and file pattern matching during test runs — they are never installed or executed in a production build.
